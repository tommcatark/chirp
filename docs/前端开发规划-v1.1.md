## 阅读指南

- 本文档是前端开发的执行清单，**按阶段顺序推进，每个阶段独立可验收**。
- 职责边界：**前端不修改任何后端代码**。所有后端需求以《后端接口规范 v1.0》交付，本文档第 5 章只列出「前端依赖后端什么」，不构成对后端的任务分配。
- 标记含义：
  - `[无]` 该步骤不依赖任何后端接口，可立即开工
  - `[就绪]` 该步骤所依赖的后端接口**已实现并编译通过**，可直接联调（v1.1 新增，替代 v1.0 的 `[改造]`/`[新增]` 语义）
  - `[待修]` 依赖后端先修掉一个既有缺陷
  - 遗留的 `[改造]` / `[新增]` 仅出现在第 5 章，用于说明「后端相对初始状态的改动性质」，不代表当前仍缺失。
- 术语：**mock 层** = 前端内置的假接口实现，用于在后端未就绪时跑通全链路；**真接口** = 后端实际提供的 HTTP 接口。

## 2. 前置约定（来自设计文档 5.2 / 9 / 10）

| 项 | 约定 |
|---|---|
| 技术栈 | 原生 HTML/CSS/JS 多页面，零构建，不引框架；交互复杂度显著上升后再评估 Vue/React |
| 文件组织 | 一页一 `html` + 一同名 `js`；公共能力只进 `shared.js`，页面内不重复实现 |
| 渲染安全 | 所有用户输入必须过 `escapeHTML`，禁止 innerHTML 直插未转义数据 |
| 鉴权 | 写操作一律带 `Authorization: Bearer <token>`；401 清 storage → 跳 `/index.html?next=<当前页>` |
| 校验 | 前端校验只是体验层，后端为准；错误文案取响应体 `message` 字段，不自行翻译或拼接 |
| 分页 | `offset + limit`，默认 20、最大 50；返回 `{items, total, offset, limit, hasMore}` |
| 错误码 | 400 参数 / 401 未登录 / 403 越权 / 404 不存在 / 409 冲突 / 500 服务异常 |
| 命名 | 常量 `UPPER_SNAKE`、函数 `camelCase`、DOM id `kebab-case` |
| 注释 | 关键功能与关键技术写中文注释（沿用后端规范） |
| CSP | 沿用 `server.mjs` 现有策略；**仅当新增外部资源时**才修改（`connect-src 'self' http://localhost:8080`） |

### 2.1 鉴权方案补充说明（v1.1 新增）

规范 D1 已定：**DB token + Redis，不用 JWT**。前端只需按标准 Bearer 语义写，具体机制如下，供排障时参考：

| 环节 | 说明 |
|---|---|
| 签发 | `POST /api/auth/register` / `/login` 返回 `token`（64 位随机 hex 字符串）+ `expiresAt`（ISO-8601） |
| 存储 | 服务端：Redis `chirp:token:{token}` → `userId`，TTL 7 天；同时落 `tokens` 表 |
| 传输 | 前端每次携带 `Authorization: Bearer <token>` |
| 网关校验 | `chirp-gateway` 的 `JwtAuthGlobalFilter`（`order = -100`）从 Redis 校验 token 是否存在，无效统一返回 `{"message":"登录已失效，请重新登录"}`（401） |
| 放行清单 | `/api/auth/**`、`GET /api/posts/**`、`GET /api/users/{id}`、`GET /api/users/{id}/posts|followers|following`、`GET /api/search`、`GET /api/posts/{id}/comments`、`/actuator/**` |
| 登出 | `POST /api/auth/logout` 返回 **204 No Content**，服务端删除 Redis 与 DB 中的 token → 前端 `request()` 需把 204 当成功且 `data` 为 `null` |
| 前端存储键 | `chirpToken`（token）、`chirpUser`（用户信息，含 `id/name/email/handle/avatarUrl`） |

> ⚠️ 代码里残留的 `JwtService`、`chirp.jwt.*` 配置项、jjwt 依赖为**历史遗留死代码**，零引用，不影响前端。前端不要依赖任何 JWT 语义（如解析 payload 取用户 ID）。

### 3.2 mock 层的定位调整（v1.1 修订）

v1.0 把 `mock/` 当作「等后端期间的主力」。**后端已全部就绪后，`mock/` 的职责收缩为**：

1. **离线兜底**：后端未启动时页面仍可演示，不白屏。
2. **契约回归**：把《后端接口规范 v1.0》的 25 个接口逐条写成 mock 实现，当后端行为漂移时用 `USE_MOCK` 对比排查。
3. **异常路径测试**：可主动注入 400 / 401 / 403 / 404 / 409 / 500，验证前端的错误分支 —— 真接口下这些路径很难复现。

> 因此 `mock/` **仍然要做**，但优先级从「Phase 0 必须产出」降为「Phase 0 产出骨架 + Phase 5 前补全异常注入」。Phase 1–4 的开发主路径改为**直连真接口**。

### 5.3 需要注意的契约细节（前端易踩坑）

| # | 细节 | 说明 |
|---|---|---|
| ① | 分页是**统一包装** | 所有列表接口返回 `{items, total, offset, limit, hasMore}`。v1.0 担心的「裸数组兼容」风险**已消除**，前端不要再写兼容分支 |
| ② | `limit` 上限 50，**超出不报错** | 传 999 后端按 50 处理并返回 200（T02）。前端 `renderPager` 不必做上限校验 |
| ③ | `GET /posts` 的 `scope` 只有 `latest` / `following` | `following` 未登录 → **401**（不是返回空列表） |
| ④ | 三个接口返回 **204 无响应体** | `POST /auth/logout`、`DELETE /posts/{id}`、`DELETE /comments/{id}`。`request()` 必须把 204 当成功且 `data = null` |
| ⑤ | 两个接口返回 **201 Created** | `POST /posts`、`POST /posts/{id}/comments` |
| ⑥ | 评论**升序**，帖子**倒序** | `GET /posts/{id}/comments` 按 `createdAt` ASC；`GET /posts` 按 DESC |
| ⑦ | `POST /posts` 请求体**只有 `content`** | 后端从 token 解析作者。前端传 `userId` 也不会被采纳（规范 D3 禁止信任请求体 userId） |
| ⑧ | 字符按 **Unicode 码点**计 | 后端用 `codePointCount`。前端 `String.length` 会把 emoji 算 2，**校验会与后端不一致**（见 Q5） |
| ⑨ | `reposts` 字段恒为 0 | 后端 `toResponse` 硬编码传 `0`，转发功能本期后置。前端**不要渲染转发按钮** |
| ⑩ | `GET /search` 的 `type` 必填 | 只接受 `post` / `user`，无 `all`。必须并发两次请求 |
| ⑪ | `PUT /users/me` 三字段全可选 | 但**至少传一个**，否则 400「没有需要更新的内容」。只传 `name` 时 bio/avatarUrl 不动 |
| ⑫ | `avatarUrl` 可为 `null` | `PostResponse.authorAvatarUrl` / `UserResponse.avatarUrl` 都可能为 `null`，前端需回退到首字母头像（`avatarHTML` 已具备此能力） |
| ⑬ | `GET /users/me` 是**唯一**返回 `email` 的接口 | 其他用户接口不下发 email；`handle` 由后端从 email 前缀派生 |
| ⑭ | 通知摘要是**前 50 字符**硬截断 | `postExcerpt` / `commentExcerpt` 由后端截断，前端直接展示即可 |
| ⑮ | 级联删除 | 帖子被删后，其评论 / 点赞级联删除；指向该帖的通知的 `postExcerpt` 变 `null` |

## 8. 开工顺序

```
Phase 0 ──评审──> Phase 1 ──评审──> Phase 2 ──评审──> Phase 3 ──评审──> Phase 4 ──评审──> Phase 5
  ↑                                                                                    ↑
零后端依赖，可立即开工                                                        需后端全部就绪
```

**推荐一次做完 Phase 0，再逐阶段推进。**

理由：Phase 0 既零后端依赖，又一次性收敛了 4 个既有缺陷与全部重复代码。跳过它直接写新页面，会导致 4 个新页面各抄一遍工具函数与网络层，后续必须回头重构。

**v1.1 补充的开工前置**：

1. 后端应用 `docs/fix-gateway-redis-dependency.patch`（否则网关起不来）。
2. 用户在自己的终端执行 `bash start-all.sh`，确认 4173 / 8080 / 8081 三端口就绪。
3. `git fetch --all --prune` 确认 `dev_cm` 未落后于 `origin/dev`。
