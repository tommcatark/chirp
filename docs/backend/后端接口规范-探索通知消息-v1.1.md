# 后端接口规范 · 探索 / 通知 / 消息（v1.1）

> 面向后端开发者的实现规格。本文件描述前端「探索页、通知页、消息页」实际调用的全部接口契约，字段名、类型、状态码、校验规则均以本文为准。
> 上一版整体规范见 `后端接口规范-v1.0.md`；本文件只补充/确认这三块功能，冲突时以本文件为准。

---

## 1. 通用约定

### 1.1 入口与路由

所有请求经网关统一入口，基址 `http://localhost:8080`。

| 网关路由 | 目标服务 | 端口 | 本文涉及的接口 |
|---|---|---|---|
| `/api/posts/**` | chirp-posts | 8082 | `GET /api/posts` |
| `/api/search/**` | chirp-posts | 8082 | `GET /api/search` |
| `/api/hashtags/**` | chirp-posts | 8082 | `GET /api/hashtags/trending` |
| `/api/users/**` | chirp-users | 8083 | `GET /api/users/{id}`、`POST/DELETE /api/users/{id}/follow` |
| `/api/notifications/**` | chirp-social | 8084 | `GET /api/notifications`、`POST /api/notifications/read` |
| `/api/messages/**` | chirp-social | 8084 | 消息页 5 个接口 |

CORS 允许来源：`http://localhost:4173`（前端静态服务器）。

### 1.2 认证

- 请求头：`Authorization: Bearer {token}`。
- `token` 来源：`POST /api/auth/login`（或注册）返回的 64 位随机字符串，服务端存 Redis，通过 `TokenStoreService.getUserId(token)` 解析出用户 id。
- **可选认证**：探索页的搜索、趋势、最新帖、用户详情允许访客访问（不传 token），此时响应中的 `liked` / `mine` / `followedByMe` / `me` 一律为 `false`。
- **强制认证**：通知列表、通知已读、消息全部接口、关注/取关。token 缺失或失效时必须返回：

```http
HTTP/1.1 401 Unauthorized
{"message": "登录已失效，请重新登录"}
```

### 1.3 分页

除趋势榜外，所有列表接口统一返回 `PageResponse`，**不得直接返回裸数组**：

```json
{
  "items": [],
  "total": 0,          // 符合条件的总条数，不受 limit 影响
  "offset": 0,
  "limit": 20,
  "hasMore": false     // 等价于 offset + items.length < total
}
```

- `limit` 上限 50，超过按 50 处理（不报错）；`limit < 1` 按 1 处理。
- 分页参数 `offset` 以「条数」为单位；实现上按 `PageRequest.of(offset / limit, limit)` 换算。
- 前端分页时用 `hasMore` 判断是否展示「加载更多」。

> 例外：`GET /api/hashtags/trending` 返回裸数组（历史约定，前端已按数组处理）。

### 1.4 错误响应

统一（非 401 时也一致）：

```json
{"message": "具体错误说明"}
```

### 1.5 时间与字段类型

- 所有时间字段为 ISO-8601 UTC 字符串，例如 `"2026-10-23T12:34:56Z"`（Java `Instant`）。
- 主键为 `Long`；分页计数为 `long`。
- 布尔字段命名：`liked`、`mine`、`me`、`followedByMe`、`isRead`（注意 `isRead` 保留 `is` 前缀，前端按此读取）。

## 2. 探索页接口

前端页面 `explore.html` / `explore.js`。页面由三部分组成：搜索结果（帖子 / 用户双 tab）、趋势话题、活跃作者与最新鸣响。

**前端实际调用顺序**

| 顺序 | 接口 | 用途 |
|---|---|---|
| 1 | `GET /api/hashtags/trending?limit=10` | 「正在鸣响」趋势话题 |
| 2 | `GET /api/posts?scope=latest&limit=30` | 「最新鸣响」列表，并从中聚合作者 |
| 3 | `GET /api/users/{id}` ×N | 活跃作者卡片详情（关注状态、粉丝数） |
| 4 | `GET /api/search?q=&type=&limit=30` | 用户输入关键词后搜索（300ms 防抖 / 回车） |
| 5 | `POST` / `DELETE /api/users/{id}/follow` | 关注 / 取关 |

### 2.1 GET /api/search — 搜索

| 参数 | 位置 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|---|
| `q` | query | string | 是 | — | 关键词，服务端 `trim()` 后不得为空 |
| `type` | query | string | 是 | — | 枚举 `post`（搜帖子）/ `user`（搜用户） |
| `offset` | query | int | 否 | 0 | 分页偏移 |
| `limit` | query | int | 否 | 20 | 每页条数，上限 50 |

**校验**

- `q` 去空格后为空 → `400 {"message":"搜索关键词不能为空"}`
- `type` 不是 `post` / `user` → `400 {"message":"搜索类型不合法"}`

**匹配语义**

- `type=post`：对帖子正文做**不区分大小写的包含匹配**（`LOWER(content) LIKE '%q%'`），按 `createdAt DESC` 排序。
- `type=user`：对用户昵称做不区分大小写的包含匹配（`LOWER(name) LIKE '%q%'`）。
- 不搜索邮箱、handle、话题名（话题名搜索走趋势榜）。

**响应 `type=post`**：`PageResponse<PostResponse>`

```json
{
  "items": [
    {
      "id": 12,
      "userId": 1,
      "authorName": "张三",
      "authorHandle": "zhangsan",
      "authorAvatarUrl": null,
      "content": "今天天气不错 #晴天#",
      "createdAt": "2026-10-23T08:00:00Z",
      "likes": 3,
      "reposts": 0,
      "comments": 1,
      "liked": false,
      "mine": false
    }
  ],
  "total": 1, "offset": 0, "limit": 30, "hasMore": false
}
```

**响应 `type=user`**：`PageResponse<UserResponse>`，字段见 §5.2。

说明：`reposts` 暂恒为 `0`（转发功能未实现），保持字段存在以便前端兼容。

### 2.2 GET /api/hashtags/trending — 趋势话题

| 参数 | 类型 | 默认 | 约束 |
|---|---|---|---|
| `limit` | int | 5 | 1–20，超出按边界值处理 |

**响应：裸数组**（不包裹 PageResponse）

```json
[
  {"tag": "晴天", "postCount": 4},
  {"tag": "读书", "postCount": 2}
]
```

**统计语义（必须与之一致，前端不需要额外处理）**

- 取最近 `200` 条帖子（按 `createdAt DESC`）作为扫描窗口。
- 话题识别正则：`#([^#\s]{1,30})#` 或 `#([^#\s]{1,30})(?=\s|$)`，即支持 `#标签#` 与 `#标签 ` 两种写法，标签长度 1–30，不含 `#` 与空白。
- **同一条帖子内同一标签只计一次**（去重）。
- 按出现帖数 `postCount` 倒序，取前 `limit` 个。
- 无话题时返回 `[]`（前端显示空态，不报错）。

访客可访问，无需 token。

### 2.3 GET /api/posts — 信息流（探索页取最新、首页取推荐/关注）

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `scope` | string | `latest` | `latest` 全站最新；`following` 关注的人 |
| `offset` | int | 0 | 分页偏移 |
| `limit` | int | 20 | 每页条数，上限 50 |

**规则**

- `scope=latest`：按 `createdAt DESC` 返回全部帖子，访客可访问。
- `scope=following`：**必须登录**，token 缺失/失效 → `401`。取当前用户关注的所有人（`follows.followeeId`）的帖子，按 `createdAt DESC`；若关注列表为空，返回 `total=0` 的空 `PageResponse`（不得返回 401 或 404）。
- 其它 `scope` 值按 `latest` 处理。

**响应**：`PageResponse<PostResponse>`，字段同 §2.1。

前端探索页固定使用 `scope=latest&limit=30`。

### 2.4 GET /api/users/{id} — 用户详情（活跃作者卡片）

| 参数 | 位置 | 说明 |
|---|---|---|
| `id` | path | 用户 id |

- 用户不存在 → `404 {"message":"用户不存在"}`
- 访客可访问；传 token 时正确填充 `followedByMe` 与 `me`。

响应 `UserResponse`，字段见 §5.2。前端用到：`id`、`name`、`handle`、`bio`、`followerCount`、`followedByMe`、`me`。

### 2.5 POST / DELETE /api/users/{id}/follow — 关注 / 取关

**必须登录**，否则 401。

**POST（关注）**

- `id` 等于当前用户 → `400 {"message":"不能关注自己"}`
- 用户不存在 → `404 {"message":"用户不存在"}`
- 幂等：已关注时再次调用不报错、不重复插入。
- 首次关注成功后，**必须为被关注者生成一条 `type=follow` 的通知**（`actorId=当前用户`，`postId=null`，`commentId=null`）。

**响应（POST / DELETE 同构）**

```json
{"following": true, "followerCount": 12}
```

`DELETE` 为幂等取消关注，`following=false`。

## 3. 通知页接口

前端页面 `notifications.html` / `notifications.js`；首页导航角标也依赖本接口的 `unreadCount`。

### 3.1 GET /api/notifications — 通知列表

**必须登录**。

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `offset` | int | 0 | 分页偏移 |
| `limit` | int | 20 | 每页条数，上限 50 |

**响应**（在 `PageResponse` 基础上**额外**包含 `unreadCount`）

```json
{
  "items": [
    {
      "id": 88,
      "type": "comment",
      "actor": {"id": 2, "name": "李四", "handle": "lisi", "avatarUrl": null},
      "postId": 12,
      "postExcerpt": "今天天气不错 #晴天#",
      "commentId": 45,
      "commentExcerpt": "写得真好",
      "isRead": false,
      "createdAt": "2026-10-23T09:10:00Z"
    }
  ],
  "total": 3,
  "offset": 0,
  "limit": 20,
  "hasMore": false,
  "unreadCount": 1
}
```

**字段规则**

- `type` 枚举：`like` / `comment` / `follow`。
- `actor`：`{id, name, handle, avatarUrl}`；用户已删除时 `name="未知用户"`、`handle="unknown"`、`avatarUrl=null`（不得为 null 整个 actor 对象）。
- `postExcerpt`：帖子正文前 50 字符；`type=follow` 或帖子已删除时为 `null`。
- `commentExcerpt`：评论正文前 50 字符；仅 `type=comment` 有值，其余为 `null`。
- 排序：`createdAt DESC`。
- `unreadCount`：当前用户全部未读通知数（**不受分页影响**，每页都要返回准确值）。

**通知产生规则（写入方）**

| 触发动作 | 接收者 | type | postId | commentId | 不产生通知的情况 |
|---|---|---|---|---|---|
| 点赞帖子 | 帖子作者 | `like` | 帖子 id | null | 自己赞自己的帖子 |
| 评论帖子 | 帖子作者 | `comment` | 帖子 id | 新评论 id | 自己评论自己的帖子 |
| 关注用户 | 被关注者 | `follow` | null | null | 重复关注（幂等，不重复通知） |

### 3.2 POST /api/notifications/read — 标记已读

**必须登录**。请求体可为空对象或省略。

| 请求体 | 行为 |
|---|---|
| `{}` 或 `{"ids": []}` 或省略 | 将当前用户**全部**未读通知标记为已读 |
| `{"ids": [88, 89]}` | 仅标记这些 id 中**属于当前用户**的通知 |

- 必须带 `userId` 条件，防止越权修改他人通知。
- 已读操作不报错（幂等）。

**响应**

```json
{"unreadCount": 0}
```

> 实现注意：`@Modifying` 的 JPQL `UPDATE` **必须**同时加 `@Transactional`，否则运行时会 500（本项目曾出现过该问题）。

## 4. 消息页接口（私信）

前端页面 `messages.html` / `messages.js`；首页导航「消息」角标依赖 `GET /api/messages/unread-count`。

数据模型：`messages(id, sender_id, recipient_id, content, is_read, created_at)`，外键指向 `users(id)`，`ON DELETE CASCADE`。

### 4.1 GET /api/messages/conversations — 会话列表

**必须登录**。

**响应**

```json
{
  "items": [
    {
      "user": {"id": 2, "name": "李四", "handle": "lisi", "avatarUrl": null},
      "lastMessage": {
        "id": 101, "senderId": 2, "recipientId": 1,
        "content": "收到张三，这是回复", "isRead": false,
        "createdAt": "2026-10-23T09:20:00Z"
      },
      "unreadCount": 1
    }
  ],
  "totalUnread": 1
}
```

**语义**

- 每个「对话对象」只出现一次：与自己有消息往来的每个用户一条。
- `lastMessage` 取该对话中 `id` 最大（即最新）的一条。
- 排序：按 `lastMessage.createdAt DESC`（最新会话在最前）。
- `unreadCount`：该对话中**对方发给我的未读消息数**（`recipient_id=我 && sender_id=对方 && is_read=false`）。
- `totalUnread`：全部未读私信总数。
- 没有会话时返回 `{"items": [], "totalUnread": 0}`（前端显示空态）。
- `user` 为用户摘要；用户已删除时 `name="未知用户"`、`handle="unknown"`。

### 4.2 GET /api/messages — 获取与某人的消息

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `with` | Long | — | **必填**，对话对方用户 id |
| `offset` | int | 0 | 分页偏移 |
| `limit` | int | 30 | 每页条数，上限 50 |

- `with` 用户不存在 → `404 {"message":"用户不存在"}`
- 返回双方往来的消息：`(sender=我 AND recipient=对方) OR (sender=对方 AND recipient=我)`。

**响应**：`PageResponse<MessageResponse>`

```json
{
  "items": [
    {
      "id": 101, "senderId": 2, "recipientId": 1,
      "content": "收到张三，这是回复", "isRead": false,
      "createdAt": "2026-10-23T09:20:00Z"
    }
  ],
  "total": 2, "offset": 0, "limit": 30, "hasMore": false
}
```

**排序必须为 `createdAt DESC`（最新在前）**。前端渲染时会自行 `reverse()` 成正序气泡流，并用 `hasMore` + 追加到列表顶部实现「加载更早消息」。后端不要改成升序。

### 4.3 POST /api/messages — 发送私信

**必须登录**。

**请求体**

```json
{"recipientId": 2, "content": "你好"}
```

| 校验 | 状态码 | message |
|---|---|---|
| 缺少 `recipientId` | 400 | `缺少接收者` |
| `content` 去空格后为空、或长度 > 500 | 400 | `消息内容需为 1-500 字符` |
| `recipientId` 等于当前用户 | 400 | `不能给自己发消息` |
| 接收者不存在 | 404 | `用户不存在` |

- `content` 需 `trim()` 后落库。
- 发送成功后发送方的会话列表、接收方的未读数应即时变化。

**响应：`201 Created`**

```json
{
  "id": 102, "senderId": 1, "recipientId": 2,
  "content": "你好", "isRead": false,
  "createdAt": "2026-10-23T09:30:00Z"
}
```

（返回完整 `MessageResponse`，前端直接用它渲染新气泡。）

### 4.4 POST /api/messages/read — 标记与某人的会话已读

**必须登录**。

**请求体**

```json
{"with": 2}
```

- `with` 缺失 → `400 {"message":"缺少会话对象"}`
- 行为：把 `recipient_id=我 AND sender_id=with AND is_read=false` 的消息全部置为已读。
- 幂等。

**响应**

```json
{"unreadCount": 0}
```

（`unreadCount` 为当前用户全部未读私信数，前端用它刷新首页角标。）

### 4.5 GET /api/messages/unread-count — 未读私信总数

**必须登录**。供首页导航角标使用。

```json
{"unreadCount": 3}
```

无人发消息时返回 `{"unreadCount": 0}`。

## 5. 数据结构附录

### 5.1 PostResponse

| 字段 | 类型 | 说明 |
|---|---|---|
| id | Long | 帖子 id |
| userId | Long | 作者 id |
| authorName | String | 作者昵称；作者已删除时 `"未知用户"` |
| authorHandle | String | 作者 handle（由邮箱 @ 前部分推导）；已删除时 `"unknown"` |
| authorAvatarUrl | String \| null | 头像 URL |
| content | String | 正文，1–500 字符 |
| createdAt | String(ISO-8601) | 发布时间 |
| likes | long | 点赞数 |
| reposts | long | 转发数，暂恒为 0 |
| comments | long | 评论数 |
| liked | boolean | 当前请求者是否已点赞；访客 `false` |
| mine | boolean | 是否为当前请求者发布；访客 `false` |

### 5.2 UserResponse

| 字段 | 类型 | 说明 |
|---|---|---|
| id | Long | 用户 id |
| name | String | 昵称 |
| handle | String | 邮箱 @ 前部分 |
| bio | String \| null | 简介 |
| avatarUrl | String \| null | 头像 |
| createdAt | String(ISO-8601) | 注册时间 |
| postCount | long | 发帖数 |
| followingCount | long | 关注数 |
| followerCount | long | 粉丝数 |
| followedByMe | boolean | 当前用户是否已关注 TA；访客 `false` |
| me | boolean | 是否为当前用户本人；访客 `false` |

### 5.3 NotificationResponse

见 §3.1。

### 5.4 MessageResponse / ConversationResponse

见 §4.1、§4.2、§4.3。

### 5.5 错误响应

```json
{"message": "..."}
```

## 6. 数据库要求

存储层按现有约定使用 PostgreSQL，表结构由 `chirp_schema.sql` 维护（Hibernate `ddl-auto` 仅兜底）。

### 6.1 notifications

| 列 | 类型 | 约束 |
|---|---|---|
| id | BIGSERIAL | PK |
| user_id | BIGINT | NOT NULL，FK → users(id) ON DELETE CASCADE（接收者）|
| actor_id | BIGINT | NOT NULL，FK → users(id) ON DELETE CASCADE（触发者）|
| type | VARCHAR(20) | NOT NULL，`like` / `comment` / `follow` |
| post_id | BIGINT | NULL，FK → posts(id) ON DELETE CASCADE |
| comment_id | BIGINT | NULL，FK → comments(id) ON DELETE CASCADE |
| is_read | BOOLEAN | NOT NULL DEFAULT false |
| created_at | TIMESTAMPTZ | NOT NULL DEFAULT now() |

索引：`(user_id, created_at DESC)`、`(user_id, is_read)`。

### 6.2 messages

| 列 | 类型 | 约束 |
|---|---|---|
| id | BIGSERIAL | PK |
| sender_id | BIGINT | NOT NULL，FK → users(id) ON DELETE CASCADE |
| recipient_id | BIGINT | NOT NULL，FK → users(id) ON DELETE CASCADE |
| content | VARCHAR(500) | NOT NULL，CHECK `char_length(content) BETWEEN 1 AND 500` |
| is_read | BOOLEAN | NOT NULL DEFAULT false |
| created_at | TIMESTAMPTZ | NOT NULL DEFAULT now() |

约束与索引：

- `CHECK (sender_id <> recipient_id)` — 禁止给自己发消息。
- `idx_messages_sender_id (sender_id)`
- `idx_messages_recipient_id (recipient_id)`
- `idx_messages_pair_created (sender_id, recipient_id, created_at DESC)` — 会话查询复合索引。

## 7. 前端调用对照表（验收依据）

| 页面 | 调用 | 依赖的响应字段 |
|---|---|---|
| explore.js | `GET /api/search?q=&type=post|user&limit=30` | `items`（`PostResponse` / `UserResponse`） |
| explore.js | `GET /api/hashtags/trending?limit=10` | 数组元素 `tag`、`postCount` |
| explore.js | `GET /api/posts?scope=latest&limit=30` | `items`（`userId`、`authorName`、`authorHandle`、`content`、`createdAt`、`comments`、`likes`） |
| explore.js | `GET /api/users/{id}` | `name`、`handle`、`bio`、`followerCount`、`followedByMe`、`me` |
| explore.js | `POST/DELETE /api/users/{id}/follow` | 成功状态（2xx 即可） |
| notifications.js | `GET /api/notifications?offset=&limit=20` | `items`、`hasMore`、`unreadCount`；元素 `type`、`actor{id,name,handle}`、`postExcerpt`、`commentExcerpt`、`isRead`、`createdAt` |
| notifications.js | `POST /api/notifications/read`（`{}` 或 `{ids:[..]}`） | `unreadCount` |

## 8. 验收用例

### 探索

1. `GET /api/hashtags/trending?limit=10` 返回按 `postCount` 倒序的数组，无话题时为 `[]`。
2. `GET /api/search?q=&type=post` → 400「搜索关键词不能为空」。
3. `GET /api/search?q=x&type=foo` → 400「搜索类型不合法」。
4. `GET /api/search?q=天气&type=post` 能命中正文含「天气」的帖子，大小写不敏感。
5. `GET /api/search?q=张&type=user` 能命中昵称含「张」的用户，返回 `PageResponse`。
6. 访客（无 token）调 1、4、5 均成功，且 `liked`/`mine`/`followedByMe` 为 `false`。
7. 无 token 调 `GET /api/posts?scope=following` → 401。
8. 关注自己 → 400；关注不存在用户 → 404。
9. 张三关注李四后：李四 `GET /api/notifications` 中出现一条 `type=follow`，`actor.id=张三`，`postId=null`。
10. 重复关注不产生第二条通知，`followerCount` 不变。

### 通知

11. 李四点赞张三的帖子 → 张三收到 `type=like` 通知，`postId` 与 `postExcerpt` 正确。
12. 张三给自己的帖子点赞/评论 → 不产生通知。
13. 李四评论 → 张三收到 `type=comment`，`commentId`、`commentExcerpt`（≤50 字）正确。
14. `GET /api/notifications?limit=1` 返回准确 `unreadCount`，且 `total` 为总条数。
15. `POST /api/notifications/read` 空体 → 全部已读，`unreadCount=0`；未读高亮全部消失。
16. `POST /api/notifications/read {"ids":[某条属于他人的通知id]}` → 不修改他人数据，`unreadCount` 不含该条。
17. 删除帖子后，关联通知不得导致 500；`postExcerpt` 为 `null`。

### 消息

18. 张三给李四发消息 → 201，返回完整 `MessageResponse`（`isRead=false`）。
19. 李四 `GET /api/messages/conversations` → 1 个会话，`unreadCount=1`，`totalUnread=1`，`lastMessage` 为张三那条。
20. `GET /api/messages?with=1&limit=30` 返回 2 条，**倒序**（最新在前），`hasMore=false`。
21. `POST /api/messages/read {"with":1}` → `unreadCount=0`；李四会话列表 `unreadCount=0`、`totalUnread=0`。
22. 给自己发 → 400；空内容 / 501 字 → 400；不存在用户 → 404；无 token → 401。
23. 首页 `GET /api/messages/unread-count` 与 `GET /api/notifications` 的 `unreadCount` 分别驱动「消息」「通知」两个导航角标，为 0 时隐藏。
24. 会话列表在无消息时返回 `{"items":[],"totalUnread":0}`，前端展示空态而非报错。
25. 删除用户后其私信随外键级联删除，会话列表不出现孤立会话或 500。

## 9. 实现注意事项

1. `@Modifying` + JPQL `UPDATE` 必须配 `@Transactional`（标记已读接口曾因此 500）。
2. 会话列表若逐条查询用户会产生 N+1；数据量增长后应改为批量查询用户。
3. `offset / limit` 的分页换算要求 `limit >= 1`，务必先做 `Math.max(1, Math.min(limit, 50))`。
4. 所有 `userId` 必须来自 token 解析，**不得**信任请求体/查询参数中的用户 id，避免越权。
5. 通知与私信的未读数必须实时反映数据库状态，前端不做本地累加（除乐观更新外以后端返回为准）。
